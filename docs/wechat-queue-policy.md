# 微信暂停推送与普通通知合并

2026-11-11，用户反馈消息堆积，要求清空旧队列并完善小看板：检测到不可发送时暂停，
恢复后不刷出一串过期通知。本轮范围为当前会话 relay，不改变独立旧版 bridge 模式。

## 用户可见行为

- 收件或发件接口报错后暂停主动推送，继续后台接收；收到合法的本人新消息后恢复。
- 小看板显示“微信推送已暂停 · 等待新消息”，登录失效/服务停止仍优先显示各自状态。
- 待发普通进度、最终回复、成功投递回执各保留最新一条。历史 feed 再次扫描不会复活旧通知。
- 审批全文及分段、原生提问、显式选项、投递不确定警告不参与普通通知合并。
- 用户可以发送“进度”“结果”“审批”获取当前内容；恢复回信不代表自动批准请求或重新执行任务。

本地没有按“8 条”限定发送额度。本地文档中最近 8 份提问历史是采集窗口，与微信发送额度不同。
腾讯公开协议描述长轮询和回信上下文，但不提供本实现可依赖的固定回信次数/有效期保证：
https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol.md

## 数据与并发

`notification_queue.py` 保存普通通知分类和 superseded 标志。现有 relay.sqlite3 通过增列迁移，
不删除 inbox、凭据、绑定或已经送达的记录。旧库无法辨别 final/commentary 的 note 暂归 legacy_update，
待发旧 note 先合并为最新一条；新事件按实际类别替换旧更新。

被替代的通知仍为 delivered=0、superseded=1，清空正文并保留编号去重，不能解读为微信已收到。
待发数量只统计未送达且未被替代的记录。保护类消息不受普通更新数量上限约束，
其有效性仍由原审批/表单协议管理。本期没有自动清理已发送历史或为整个数据库设总容量上限。

暂停状态持久保存；旧版本尚未解除的发送退避升级为等待新消息。
一个较早网络请求失败时，先核对它实际使用的上下文，不能暂停刚刷新的新上下文。
已经在途的网络发送无法撤回；接口成功回执也不证明手机已显示。

## 改动与验证

- 新增普通通知策略文件，接入 relay_store、mirror、发送错误处理和连接状态发布。
- 原生连接模型增加可选暂停字段，兼容旧状态文件，并显示明确的暂停标签。
- 新增离线突发、保护消息、重放去重、暂停跨重启和旧库迁移测试；更新原先的自动探测预期，
  验证现在等待新消息恢复，继续检查稳定 client_id 和新上下文竞态。
- 统一入口：`bash scripts/verify.sh`，运行全部 Python 测试、两个原生入口构建及 7 组原生模型测试。
- 最终源码摘要、命令退出码和日志引用保存在 `build/verification/wechat-queue-summary.json`。

自动检查只覆盖模拟故障与原生模型；微信真实服务端限流、休眠恢复、手机最终展示需安装后实测。
本轮未更改主项目的模型、知识库或待审代码，也未改变审批权限。
未新增知识提案：这是应用层通知策略调整，代码、测试和本记录保存具体边界，不作为主项目知识规则。
